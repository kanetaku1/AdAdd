# ADR-0007: ログイン用とDrive用のGoogle Cloudプロジェクトを分離する

## ステータス

提案中 — 2026-11-20

## コンテキスト

### 2か所での登録が必要な負担

現在、委員を追加または削除するには、次の2つの作業が必要です。

1. Google Cloud Consoleで、その委員をOAuthテストユーザーとして登録（または削除）する。
2. AdAddで、その委員をユーザーとして登録（または無効化）する。

OAuth同意画面が「外部 — テスト」モードに設定されているため、テストユーザーとして登録されたアカウントしかGoogleサインインを完了できません。Consoleでの作業が必要なのはこのためです。AdAddはすでに、リクエストごとにメールアドレスを独自の`users`テーブルと`isActive`フラグで確認しています（ADR-0004の決定3および4）。

### ログインに必要なのは本人確認だけ

Googleサインインで要求するのは`openid email profile`であり、訪問者が誰であるかを確認するために必要な範囲だけです。AdAddが委員に代わってGoogle APIを呼び出すことはありません。Driveの操作には委員のアカウントではなく、専用アカウントを使用します（ADR-0006）。

### 1つのプロジェクトで一部だけを公開することはできない

Googleの同意画面の公開ステータス（「テスト」または「公開」）は、OAuthクライアントごとではなく**プロジェクトごと**に設定されます。現在のプロジェクトには、`drive`スコープを要求するDrive用OAuthクライアントもあります。このプロジェクトを公開すると、専用アカウントしか使用しないにもかかわらず、`drive`スコープがGoogleの審査対象となり、すべてのGoogleアカウントに公開されます。そのため、ログイン専用スコープとDriveスコープは別々のプロジェクトに配置し、それぞれに適した公開ステータスを設定する必要があります。

### 「外部 — テスト」モードでのリフレッシュトークンの有効期限

OAuthプロジェクトが「外部 — テスト」モードの場合、リフレッシュトークンは7日後に期限切れになります。現在のDriveクライアントがそのようなプロジェクトにある場合、専用アカウントのリフレッシュトークンを毎週再認可する必要があります。DriveをWorkspace内部のプロジェクト（「内部」）に移せば、この制限はなくなります。「内部」にできない場合は、専用アカウントだけをテストユーザーとして「外部 — テスト」モードを維持し、7日間の有効期限を運用で管理する必要があります。

## 決定

### 1. Google Cloudプロジェクトを2つに分ける

| プロジェクト | 用途 | 同意画面 | スコープ | ユーザー |
| ------- | ------- | -------------- | ------ | ----- |
| A（既存） | ログイン | 外部 — **公開** | `openid email profile` | すべてのGoogleアカウント（アクセスはAdAddが制御） |
| D（新規） | Drive | 内部（推奨）、または外部 — テスト | `drive` | 専用アカウントのみ |

### 2. ログイン用プロジェクト（A）を公開する

公開後は、すべてのGoogleアカウントでGoogleサインインを完了できます。アクセスはAdAddが制御します。

1. 委員が`/login`のGoogleボタンを押す。
2. Googleが委員を認証する（公開済みのため、テストユーザーの制限はない）。
3. `POST /auth/google`が`users`テーブルでメールアドレスを検索する。
   - 登録済みかつ`isActive = true`の場合：AdAddのセッションJWTを発行する。
   - 未登録、または`isActive = false`の場合：`403`を返す。

これは既存のフローです（ADR-0004）。変更点は、AdAddが確認する前にGoogleがアカウントを拒否しなくなることだけです。

委員の追加は、AdAddにユーザーを登録するだけになります。
委員の削除は、AdAddでユーザーを無効化するだけになります。
どちらの場合もGoogle Cloud Consoleでの作業は不要です。

### 3. Drive用プロジェクト（D）を別途作成する

新しいGoogle Cloudプロジェクトを作成します。可能であれば、専用アカウントのWorkspace組織内に作成し、「内部」に設定します。Workspace組織内に作成できない場合は、専用アカウントだけをテストユーザーとして「外部 — テスト」モードを使用します。

専用アカウントは、既存の`cmd/drive-auth`フローを使って一度認可します。生成されたリフレッシュトークンと新しいクライアント認証情報は、デプロイ用シークレットとして保存します。

### 4. `GOOGLE_DRIVE_CLIENT_ID`のデフォルト値を`GOOGLE_CLIENT_ID`にしない

`GOOGLE_DRIVE_CLIENT_ID`が空の場合に`GOOGLE_CLIENT_ID`の値をコピーする、`apps/api/internal/config/config.go`のフォールバック処理を削除します。プロジェクト分離後、この2つの値は常に異なります。

起動時の検証：

| 条件 | 結果 |
| --------- | ------ |
| Drive用の3つの環境変数（`GOOGLE_DRIVE_CLIENT_ID`、`GOOGLE_DRIVE_CLIENT_SECRET`、`GOOGLE_DRIVE_REFRESH_TOKEN`）がすべて空 | Drive連携は未設定。Driveの更新操作はサービス利用不可を返す（ADR-0006）。 |
| 3つすべてが設定済み | Drive連携を有効化する。 |
| 一部のみ設定済み | 起動エラー。部分的な設定は常に設定ミスとみなす。 |

これにより、Driveを使わないローカル開発では既存の動作を維持できます。

### 5. ログインおよびDriveのコードパスは変更しない

| コンポーネント | 変更 |
| --------- | ------ |
| ログインフロー（Google → JWT → MySQL） | なし |
| Driveフロー（専用アカウントのリフレッシュトークン） | なし |
| `AuthMiddleware`（リクエストごとのMySQL確認） | なし |
| JWTの内容と更新 | なし |

### 6. リスク：誰でもサインインを試行できる

プロジェクトを公開すると、Googleアカウントを持つ誰もがAdAddの`POST /auth/google`にアクセスできるようになります。未登録アカウントには`403`が返ります。これは許容できます。

- データは公開されない。
- 試行はAPIのアクセスログに記録される。
- 試行量に応じて、後からレート制限を追加できる（Issue #176参照）。

OAuthテストユーザーとAdAddユーザーによる二重の制限は多層防御として機能していましたが、残る制限（AdAddユーザー登録と`isActive`）で十分です。ADR-0004の決定4は、この状況を想定して設計されています。

## 移行

### 前提条件（AdAdd側）

1. このADRが承認されている。
2. `spec/operations.md`と`spec/development.md`が更新されている。
3. 決定4のコード変更（フォールバック削除と起動時検証の追加）がマージされている。

### Google Cloud Consoleでの作業

作業順が重要です。既存プロジェクトから`drive`スコープを削除する前に、新しいプロジェクトでDriveが動作することを確認します。

1. **現在の状態を確認する。** 既存プロジェクトのGoogle Auth Platformで、種類（外部）、公開ステータス（テスト）、テストユーザー、スコープ（`drive`が含まれているか）、OAuthクライアントの数を確認する。

2. **Drive用プロジェクトDを作成する。**
   - 可能であれば、専用アカウントのWorkspace組織内に新しいプロジェクトを作成する。
   - Google Drive APIを有効にする。
   - Google Auth Platformを設定する：ブランディング（アプリ名、サポートメールアドレス）、対象ユーザー（内部。不可の場合は専用アカウントだけをテストユーザーとする外部 — テスト）、データアクセス（`https://www.googleapis.com/auth/drive`）。
   - ウェブアプリケーション用OAuthクライアントを作成する。リダイレクトURIは`http://127.0.0.1:8787/callback`（`cmd/drive-auth`で使用）とする。

3. **専用アカウントを再認可する。**
   信頼できる管理者のマシンで、Git管理対象外の環境変数ファイルに新しい`GOOGLE_DRIVE_CLIENT_ID`と`GOOGLE_DRIVE_CLIENT_SECRET`を設定し、次を実行します。
   ```bash
   cd apps/api
   go run ./cmd/drive-auth -env-file <env-file>
   ```
   専用アカウントのパスキーを使って認証します。

4. **本番環境のDriveシークレットを置き換える。**
   シークレットマネージャーで`GOOGLE_DRIVE_CLIENT_ID`、`GOOGLE_DRIVE_CLIENT_SECRET`、`GOOGLE_DRIVE_REFRESH_TOKEN`を更新します。APIを再デプロイし、ファイルのアップロードとゴミ箱への移動を行って動作を確認します。

5. **ログイン用プロジェクトAを公開する。**（手順4の検証完了後にのみ実施）
   - データアクセスから`drive`を削除する（`openid email profile`のみを残す）。
   - 必要に応じてGoogle Drive APIを無効にする。
   - アプリを公開する。必要な場合に備え、ホームページURLとプライバシーポリシーURLを準備する。
   - テストユーザー一覧を整理する（ログインでは不要になる）。
   - 専用アカウントのGoogleアカウント設定（サードパーティ アクセス）から、古いDrive OAuthの許可を取り消す。

### ロールバック

手順4の後にDriveが動作しなくなった場合は、Drive用の3つのシークレットを古い値に戻して再デプロイします。この時点ではプロジェクトAはまだ変更されていません。

プロジェクトAの公開で問題が発生した場合（例：準備できていない情報をGoogleが要求した場合）は、テストモードに戻し、テストユーザーを再登録します。AdAddはこれまでどおり動作します。

## 要確認事項

移行開始前に、以下を確認する必要があります。これらはアーキテクチャやコード変更には影響しません。

- [ ] 現在のプロジェクトの状態：ログイン用とDrive用のクライアントは共用か、別々か。同意画面のスコープに`drive`が含まれているか。
- [ ] 専用アカウントのリフレッシュトークンは現在、7日ごとに期限切れになっているか。
- [ ] 「内部」を利用するため、Drive用プロジェクトDを専用アカウントのWorkspace組織内に作成できるか。組織管理者は誰か。
- [ ] 公開に必要なホームページURLとプライバシーポリシーURLは誰が準備するか。
- [ ] Consoleでの作業、再認可、本番シークレットの置き換えは誰が実施するか。実施予定日はいつか。

## 影響

### 仕様

- `spec/operations.md`：委員の追加・削除はAdAdd内だけで完結する。本番環境のDrive設定は、分離したプロジェクトを参照する。
- `spec/development.md`：`GOOGLE_DRIVE_CLIENT_ID`のフォールバックに関する説明を削除する。ログイン用プロジェクトの公開後は、MySQLモードのサインインにOAuthテストユーザー登録が不要となる。

### 実装

- `apps/api/internal/config/config.go`：`GOOGLE_DRIVE_CLIENT_ID`のフォールバックを削除し、一部のみ設定された場合の起動時検証を追加する。
- その他のコード変更はない。

### 運用

- 委員の追加：AdAdd内でユーザーを登録するだけ。
- 委員の削除：AdAdd内でユーザーを無効化するだけ。
- Google Cloud Consoleを使用するのは、OAuthクライアントの新規作成やスコープの変更など、インフラ変更の場合のみ。委員管理には使用しない。

## 検討した代替案

詳細はIssue本文を参照してください。主な代替案と採用しなかった理由は次のとおりです。

| 代替案 | 採用しなかった理由 |
| ----------- | ------------------ |
| 既存の単一プロジェクトをそのまま公開する | `drive`スコープが審査対象となり、すべてのアカウントにDriveが公開されるリスクがある。 |
| Googleサインインを完全にやめる | パスワード管理の負担が発生する。メール配信は対象外（ADR-0004）。 |
| 現在の二重登録を続ける | 運用負担が解消されない。 |
| 初回ログイン時にユーザーを自動作成する | 管理者が事前にユーザーを登録するというルールが変わる。 |
