# ADR-0007: ログイン用とDrive用のGoogle Cloudプロジェクトを分離する

## ステータス

提案中 — 2026-11-20、改訂 2026-11-24

### 改訂履歴

* 2026-11-20：初版。既存プロジェクトをログイン用として公開し、Drive用に新規プロジェクトを作成する方針。
* 2026-11-22：プロジェクトの役割を反転。既存プロジェクトをDrive用に残し、ログイン用に新規プロジェクトを作成する。Google Picker廃止（Issue #225）に伴い、ブラウザ側のGoogle認証情報が不要になったため、移行手順を簡素化。同意画面の実際の状態（`drive`スコープ未登録）を反映。
* 2026-11-24：サービスアカウント切り替え（ADR-0006改訂）を反映。個人プロジェクトのため「内部」モードは不可。サービスアカウントへの切り替えにより7日間のリフレッシュトークン期限切れの問題は解消。Drive用プロジェクトの同意画面はOAuthを使用しなくなるため実質的に無関係に。

## コンテキスト

### 2か所での登録が必要な負担

現在、委員を追加または削除するには、次の2つの作業が必要です。

1. Google Cloud Consoleで、その委員をOAuthテストユーザーとして登録（または削除）する。
2. AdAddで、その委員をユーザーとして登録（または無効化）する。

OAuth同意画面が「外部 — テスト」モードに設定されているため、テストユーザーとして登録されたアカウントしかGoogleサインインを完了できません。Consoleでの作業が必要なのはこのためです。AdAddはすでに、リクエストごとにメールアドレスを独自の`users`テーブルと`isActive`フラグで確認しています（ADR-0004の決定3および4）。

### ログインに必要なのは本人確認だけ

Googleサインインで要求するのは`openid email profile`であり、訪問者が誰であるかを確認するために必要な範囲だけです。AdAddが委員に代わってGoogle APIを呼び出すことはありません。Driveの操作には委員のアカウントではなく、専用アカウントを使用します（ADR-0006）。

### 同意画面の実際の状態

既存プロジェクトの同意画面には`drive`スコープが**登録されていない**ことが確認された。Driveの操作は以下の2つの別々の仕組みで動作しており、どちらも同意画面のスコープ設定に依存していない。

1. **バックエンド（Drive API）**：~~専用アカウントのリフレッシュトークンを使用。`cmd/drive-auth`実行時に`drive`スコープを直接リクエストして認可を取得する。「テスト」モードではGoogle側が同意画面のスコープ登録を強制しないため動作している。~~ → サービスアカウントのJSONキーで認証する方式に切り替え予定（ADR-0006改訂、Issue #238）。サービスアカウントはOAuth同意画面を経由しないため、同意画面のスコープ設定やモード（テスト/公開/内部）に一切依存しない。
2. **フロントエンド（Google Picker）**：委員個人のGoogleアカウントで`drive.metadata.readonly`を使ったOAuth同意を行い、フォルダ一覧を表示する。Picker APIは独自のOAuthポップアップで動作するため、同意画面のスコープ登録とは独立して動作する。

### Google Pickerの廃止

Issue #225で、Google Pickerをバックエンド経由のフォルダ選択UIに置き換える。これにより：

* ブラウザに公開していたGoogle認証情報（`GOOGLE_API_KEY`、Picker用の`NEXT_PUBLIC_GOOGLE_CLIENT_ID`）が不要になる。
* 委員個人のGoogleアカウントがDriveに一切関与しなくなる。
* GCPプロジェクト分離において、Picker用のClient IDの帰属先を考える必要がなくなる。

### 1つのプロジェクトで一部だけを公開することはできない

Googleの同意画面の公開ステータス（「テスト」または「公開」）は、OAuthクライアントごとではなく**プロジェクトごと**に設定される。ログイン用のOAuthクライアントを公開するには、Drive用のOAuthクライアントが別のプロジェクトに存在する必要がある。同一プロジェクトのまま公開すると、今後`drive`スコープを同意画面に登録する必要が生じた場合に審査の対象となる。

### ~~「外部 — テスト」モードでのリフレッシュトークンの有効期限~~ → サービスアカウントで解消

OAuthプロジェクトが「外部 — テスト」モードの場合、リフレッシュトークンは7日後に期限切れになります。~~DriveをWorkspace内部のプロジェクト（「内部」）に移せば、この制限はなくなります。「内部」にできない場合は、専用アカウントだけをテストユーザーとして「外部 — テスト」モードを維持し、7日間の有効期限を運用で管理する必要があります。~~

個人プロジェクトのため「内部」モードは利用できない。代わりに、Drive認証をサービスアカウント（JSONキー）に切り替えることで解決する（ADR-0006改訂、Issue #238）。サービスアカウントはJWTベースの認証を使用し、OAuthリフレッシュトークンを使用しないため、7日制限の対象外である。

## 決定

### 1. Google Cloudプロジェクトを2つに分ける

| プロジェクト | 用途 | 同意画面 | スコープ | ユーザー |
| ------- | ------- | -------------- | ------ | ----- |
| 既存 | Drive | テストのまま（サービスアカウントは同意画面に依存しない） | なし（サービスアカウントはOAuth同意画面を経由しない） | サービスアカウント |
| 新規 | ログイン | 外部 — **公開** | `openid email profile` | すべてのGoogleアカウント（アクセスはAdAddが制御） |

初版では既存プロジェクトをログイン用として公開する方針だったが、以下の理由で反転する。

* ~~既存プロジェクトのOAuthクライアントで発行済みのDrive用リフレッシュトークンがそのまま使える。**再認可もシークレット差し替えも不要**。~~ → サービスアカウントへの切り替え（ADR-0006改訂）により、既存のOAuthクライアントとリフレッシュトークンは不要になる。既存プロジェクトはサービスアカウントの作成先として残す。
* Google Picker廃止後は、既存プロジェクトのAPI KeyやClient IDをブラウザに公開する必要がなくなるため、テストモードのままで問題ない。
* ログイン用は新規プロジェクトを作るだけ。`openid email profile`のみの軽量なプロジェクトなので、公開の審査もシンプル。

### 2. ログイン用プロジェクト（新規）を公開する

公開後は、すべてのGoogleアカウントでGoogleサインインを完了できます。アクセスはAdAddが制御します。

1. 委員が`/login`のGoogleボタンを押す。
2. Googleが委員を認証する（公開済みのため、テストユーザーの制限はない）。
3. `POST /auth/google`が`users`テーブルでメールアドレスを検索する。
   - 登録済みかつ`isActive = true`の場合：AdAddのセッションJWTを発行する。
   - 未登録、または`isActive = false`の場合：`403`を返す。

これは既存のフローです（ADR-0004）。変更点は、AdAddが確認する前にGoogleがアカウントを拒否しなくなることだけです。

委員の追加は、AdAddにユーザーを登録するだけになります。
委員の削除は、AdAddでユーザーを無効化するだけになります。
どちらの場合もGoogle Cloud Consoleでの作業は不要です。

### 3. Drive用プロジェクト（既存）はそのまま残す

既存プロジェクトをDrive専用として維持する。サービスアカウントへの切り替え（ADR-0006改訂、Issue #238）により、OAuthクライアントとリフレッシュトークンは不要になる。

* ~~`GOOGLE_DRIVE_CLIENT_ID`、`GOOGLE_DRIVE_CLIENT_SECRET`、`GOOGLE_DRIVE_REFRESH_TOKEN`の値は変更不要。~~ → サービスアカウント切り替え後は`GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`に置き換え。
* ~~専用アカウントの再認可は不要。~~ → サービスアカウントはJSONキーで認証するため、再認可自体が存在しない。
* ~~可能であれば、Workspace組織の「内部」に変更してリフレッシュトークンの7日制限を解消する。~~ → 個人プロジェクトのため「内部」は不可。サービスアカウントへの切り替えにより7日制限は解消。

### 4. `GOOGLE_DRIVE_CLIENT_ID`のデフォルト値を`GOOGLE_CLIENT_ID`にしない

`GOOGLE_DRIVE_CLIENT_ID`が空の場合に`GOOGLE_CLIENT_ID`の値をコピーする、`apps/api/internal/config/config.go`のフォールバック処理を削除します。プロジェクト分離後、この2つの値は常に異なります。

**実装済み**（PR #224）。サービスアカウント切り替え（Issue #238）後は、Drive用の環境変数自体が`GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`に変わるため、このフォールバックの問題は完全に消滅する。

起動時の検証（サービスアカウント切り替え後）：

| 条件 | 結果 |
| --------- | ------ |
| `GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`が空 | Drive連携は未設定。Driveの更新操作はサービス利用不可を返す（ADR-0006）。 |
| 設定済み | Drive連携を有効化する。 |

### 5. Google Pickerを廃止し、ブラウザ側のGoogle認証情報を削除する

Issue #225で、Google Pickerをバックエンド経由のフォルダ選択UIに置き換える。これにより以下の環境変数が不要になる。

| 削除される変数 | 用途 |
| ------------- | ---- |
| `GOOGLE_API_KEY` / `NEXT_PUBLIC_GOOGLE_API_KEY` | Picker API Key |
| `NEXT_PUBLIC_GOOGLE_CLIENT_ID`（`next.config.ts`から公開） | Picker OAuth |
| `NEXT_PUBLIC_GOOGLE_DRIVE_ROOT_FOLDER_ID` | Picker の起点フォルダ（API側の`GOOGLE_DRIVE_ROOT_FOLDER_ID`は継続使用） |

`react-google-drive-picker`パッケージも削除する。

フォルダ選択はバックエンドの`GET /drive/folders`（`spec/api.md#List Drive Folders`）で専用アカウント経由で提供する。フロントエンドのUI仕様は`spec/frontend.md#Drive Upload Dialog`に記載。

### 6. ログインおよびDriveのコードパスは変更しない

| コンポーネント | 変更 |
| --------- | ------ |
| ログインフロー（Google → JWT → MySQL） | なし |
| Driveフロー | 認証方式のみ変更（OAuth → サービスアカウント、ADR-0006改訂）。Drive操作のロジックは変更なし |
| `AuthMiddleware`（リクエストごとのMySQL確認） | なし |
| JWTの内容と更新 | なし |

### 7. リスク：誰でもサインインを試行できる

プロジェクトを公開すると、Googleアカウントを持つ誰もがAdAddの`POST /auth/google`にアクセスできるようになります。未登録アカウントには`403`が返ります。これは許容できます。

- データは公開されない。
- 試行はAPIのアクセスログに記録される。
- 試行量に応じて、後からレート制限を追加できる（Issue #176参照）。

OAuthテストユーザーとAdAddユーザーによる二重の制限は多層防御として機能していましたが、残る制限（AdAddユーザー登録と`isActive`）で十分です。ADR-0004の決定4は、この状況を想定して設計されています。

## 移行

### 前提条件（AdAdd側）

1. このADRが承認されている。
2. `GOOGLE_DRIVE_CLIENT_ID`のフォールバック削除と起動時検証の追加がマージされている（**PR #224で実装済み**）。
3. Google Pickerの廃止とフォルダ選択UIの実装がマージされている（Issue #225）。

### Google Cloud Consoleでの作業

Picker廃止とプロジェクト構成の反転により、移行手順は大幅に簡素化された。

1. **ログイン用プロジェクトを新規作成する。**
   - 新しいGoogle Cloudプロジェクトを作成する。
   - Google Auth Platformを設定する：ブランディング（アプリ名、サポートメールアドレス）、対象ユーザー（外部）、データアクセス（`openid email profile`）。
   - ウェブアプリケーション用OAuthクライアントを作成する。リダイレクトURIは本番の`<APP_ORIGIN>/api/auth/google/callback`とローカル開発用の`http://localhost:3000/api/auth/google/callback`。

2. **AdAddの環境変数を更新する。**
   - `GOOGLE_CLIENT_ID`、`GOOGLE_CLIENT_SECRET`を新しいプロジェクトの値に変更する（`apps/web`とAPI検証用の両方）。
   - `GOOGLE_DRIVE_*`の3変数を`GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`に置き換える（ADR-0006改訂、Issue #238）。
   - `GOOGLE_API_KEY`を削除する（Picker廃止後）。
   - APIとWebアプリを再デプロイする。

3. **動作確認する。**
   - ログイン：テストユーザーでGoogleサインインできることを確認。
   - Drive：ファイルのアップロードとゴミ箱移動が動作することを確認。

4. **ログイン用プロジェクトを公開する。**
   - Google Auth Platformで「アプリを公開」。ホームページURLとプライバシーポリシーURLが必要な場合は準備する。
   - 公開後、テストユーザー以外のGoogleアカウントでもサインインできることを確認。

5. **既存プロジェクトをDrive専用に整理する。**
   - ログイン用OAuthクライアントが残っている場合は削除する（新プロジェクトに移行済みのため）。
   - サービスアカウント切り替え後は、Drive用OAuthクライアントも削除する（サービスアカウントはOAuthクライアントを使用しない）。
   - 旧プロジェクトのテストユーザー一覧を整理する。

### ロールバック

新しいログイン用プロジェクトに問題が発生した場合は、`GOOGLE_CLIENT_ID`と`GOOGLE_CLIENT_SECRET`を既存プロジェクトの値に戻して再デプロイする。Drive側は一切変更していないため影響なし。

## 要確認事項

移行開始前に、以下を確認する必要があります。これらはアーキテクチャやコード変更には影響しません。

- [x] 現在のプロジェクトの状態：同意画面のスコープに`drive`が含まれているか。→ **含まれていない**。
- [x] 専用アカウントのリフレッシュトークンは現在、7日ごとに期限切れになっているか。→ 「外部 — テスト」モードのため7日制限の対象。**サービスアカウント切り替え（ADR-0006改訂）により解消**。
- [x] 「内部」を利用するため、既存プロジェクトを専用アカウントのWorkspace組織に移動できるか。→ **不可**。個人プロジェクトであり組織アカウントではないため「内部」にできない。**サービスアカウントへの切り替えにより、「内部」への変更は不要**。
- [ ] 公開に必要なホームページURLとプライバシーポリシーURLは誰が準備するか。
- [ ] Consoleでの作業の担当者と実施予定日はいつか。

## 影響

### 仕様

- `spec/operations.md`：委員の追加・削除はAdAdd内だけで完結する。本番環境のDrive設定は変更不要。
- `spec/development.md`：`GOOGLE_DRIVE_CLIENT_ID`のフォールバックに関する説明を削除する。ログイン用プロジェクトの公開後は、MySQLモードのサインインにOAuthテストユーザー登録が不要となる。
- `spec/api.md`：`GET /drive/folders`エンドポイントを追加（Picker廃止の代替）。
- `spec/frontend.md`：Drive Upload Dialogの仕様を更新（Pickerからフォルダブラウザへ）。

### 実装

- `apps/api/internal/config/config.go`：`GOOGLE_DRIVE_CLIENT_ID`のフォールバックを削除し、一部のみ設定された場合の起動時検証を追加する。**PR #224で実装済み**。サービスアカウント切り替え後は環境変数を`GOOGLE_DRIVE_SERVICE_ACCOUNT_KEY`に変更（Issue #238）。
- `apps/api/internal/service/drive_service.go`：`driveClient()`メソッドをOAuth → サービスアカウントJWT認証に変更（Issue #238）。
- `apps/api/cmd/drive-auth/`：サービスアカウント切り替え後に削除（Issue #238）。
- `apps/api`：`GET /drive/folders`エンドポイントの追加（Issue #225）。
- `apps/web`：Google Pickerの廃止とフォルダ選択UIの実装（Issue #225）。`react-google-drive-picker`パッケージの削除。`next.config.ts`からPicker用環境変数の公開を削除。
- `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`の値を新プロジェクトに変更する（環境変数の差し替えのみ、コード変更なし）。

### 運用

- 委員の追加：AdAdd内でユーザーを登録するだけ。
- 委員の削除：AdAdd内でユーザーを無効化するだけ。
- Google Cloud Consoleを使用するのは、OAuthクライアントの新規作成やスコープの変更など、インフラ変更の場合のみ。委員管理には使用しない。

## 検討した代替案

詳細はIssue #198の本文を参照。主な代替案と採用しなかった理由は次のとおりです。

| 代替案 | 採用しなかった理由 |
| ----------- | ------------------ |
| 既存の単一プロジェクトをそのまま公開する | Drive用のOAuthクライアントが同居しており、将来`drive`スコープの登録が必要になった場合に審査対象となるリスクがある。 |
| 既存プロジェクトをログイン用にして新規でDriveプロジェクトを作る（初版の方針） | 専用アカウントの再認可とシークレット差し替えが必要になる。反転する方が移行が簡単。 |
| Googleサインインを完全にやめる | パスワード管理の負担が発生する。メール配信は対象外（ADR-0004）。 |
| 現在の二重登録を続ける | 運用負担が解消されない。 |
| 初回ログイン時にユーザーを自動作成する | 管理者が事前にユーザーを登録するというルールが変わる。 |
